# progress/ — プラン実行中の進捗・詳細記録（サンプル）

> `.claude/plans/references/progress/` 配下のサンプル。プラン実行中に生じた「詳細な調査結果・実装メモ・計画との差分の理由・後続ステップへの引継ぎ」を、メインのプランファイル（`references/` 直下のファイル）とは別にまとめる場所の書き方を示す。実装対象ではありません。

## なぜ progress フォルダを分けるか

プランファイル（`00-overview.md` / `01-*.md` / …）は、実装者が「次に何をすればよいか」を一目で把握するための**目次・導線**として保ちたい。実行が進むたびに調査の生ログ・実装の細かい判断・差分の理由をプランファイル本体へ追記していくと、スキャン性が落ち、本来の「やること・触るファイル・決定事項」が埋もれてしまう。

だから:

- **プランファイル本体（`references/` 直下、実際のプランでは `<機能名>/` 直下）には薄い導線だけ残す** — ステップ完了マーク（✅）、1〜2行の状態行、計画通りにいなかった場合の差分サマリ（＋ progress へのリンク）、調査結果の要約（＋ progress へのリンク）
- **詳細は `progress/` 配下にまとめる** — 生の調査データ、実装中の判断のフル文脈、差分が発生した理由の詳細、後続ステップ・後続タスクへの引継ぎ事項

## 何をどこに書くか

| 情報                                                          | プランファイル本体      | progress/ |
| ------------------------------------------------------------- | ----------------------- | --------- |
| ステップの完了状態                                            | ✅マーク・1行の状態行   | —         |
| 調査結果の要約（後続ステップが前提にする事実）                | 数行の箇条書き + リンク | —         |
| 調査の生データ（APIレスポンス例・比較表・読んだページの抜粋） | —                       | ✅        |
| 計画通りにいかなかった変更のサマリ                            | 1〜2行 + リンク         | —         |
| 上記変更の理由・背景の詳細                                    | —                       | ✅        |
| 実装中にその場で決めた細かい判断                              | —                       | ✅        |
| 後続ステップ／後続タスクへの引継ぎ事項                        | —                       | ✅        |

「クリティカルな内容（計画どおりにいかず変更した内容・実装進捗）」はプランファイル本体に薄く残し、「詳細な実装内容・後続タスクへの引継ぎ」は progress にまとめる、という棲み分け。

## progress ファイルの命名

- `{ステップ番号2桁}-{短いスラッグ}.md` — 例: `01-research-results.md` / `02-implementation-notes.md`
- ステップに紐付かない横断的な内容（複数ステップにまたがる手戻りや、後続タスクへの引継ぎまとめ）は `99-{スラッグ}.md`
- 1ステップの実行で詳細が複数の観点に分かれるなら、`02-implementation-notes.md` / `02-error-handling-decision.md` のようにステップ番号で揃えて複数ファイルに分けてよい。1ファイルに無理に詰め込まない

## いつ progress ファイルを作るか

- プランファイル本体の節に「これ以上書くと3〜4行を超えて埋もれる」と感じた瞬間が作成タイミング
- 逆に、1〜2行で済む調査結果や差分は progress ファイルを作らずプランファイル本体に直接書いてよい。progress フォルダが空のまま実装が終わっても問題ない
- 目安は「プランファイル本体の1節が、本来の5要素（やること／読むべきファイル／触るファイル／決定事項／ルール更新）以外のメモで埋まり始めたら分離」

## task-tracker との棲み分け（セッションをまたぐTODO化）

progress は「プラン1件の実行中に生じた詳細」をプランと同じディレクトリ内にまとめるもの。一方で [task-tracker](../../../skills/task-tracker/SKILL.md) スキルは `.claude/tasks/<task-name>/CURRENT.md` に「今の現状・次にやること」を残し、複数セッションを行き来する際の再開導線にする。両者は別物で、重複させない:

- **1セッションで完結するプラン**: progress も task-tracker も不要なことが多い（[../03-single-file-example.md](../03-single-file-example.md) 参照）。
- **セッションをまたぐプラン**: プラン本体の✅マーク（ステップ完了）はプラン側、進行中の細かい現状は task-tracker の `CURRENT.md` 側、実行中に生じた詳細（差分の理由・実装メモ・後続引継ぎ）は引き続き progress 側、と3層で棲み分ける。task-tracker の「関連ファイル」節からプラン・progress へリンクを張れば、再開時に一発で辿れる。

## 新規プランを書くとき

progress フォルダは実行開始時点では空でよい（存在しなくてよい）。実行が進んで初めて詳細が溜まったときに作る。テンプレートとしてプランを新規作成するときに progress フォルダを予め作る必要はない。

## 書き方のポイント

- **progress は「プランファイル本体を読む人が原則読まなくても実装を進められる」ようにする。** 本体の要約だけで次に進めるようにし、詳細が必要になったときの参照元として progress を残す。だから progress 側には「後続ステップへの引継ぎ事項」を明示的に列挙し、本体側はそのリンクだけを置く。
- **progress に書くのは「実行してみないと分からなかったこと」に限る。** プラン立案時に既に分かっている決定事項・落とし穴は最初からプランファイル本体の決定事項表に書くべきで、progress に後追いで書くものではない。
- **progress は自由形式でよい。** プランファイル本体のような5要素のフォーマットに縛られない。見出しは「計画との差分／実装メモ／後続タスクへの引継ぎ」など内容に合わせて自由に立てる。
- **progress はプランファイル本体と一緒にGit管理する。** 実行時の一時メモではなく、次に同じ領域を触る人のための参照記録として残す。ただし調査で叩いた生のAPIレスポンスなど長すぎる生データは要約に留め、本当に必要な抜粋だけを残す。
