# 郵便番号からの住所自動入力機能 ラフプラン（サンプル）

> `plans/{plan-name}/rough/` に置くラフプランのサンプル。実装対象ではありません。詳細プランへ移行済みの状態（`status: promoted`）で、新規ラフプランは `status: drafting` から書き始める（値の意味は [rough-plan.md](../../../guides/rough-plan.md)）。

## 何がしたいか（ざっくり）

会員登録フォームの郵便番号欄で、住所を自動入力したい。外部APIを使う方向で考えているが、どのAPIがいいか、レスポンス形式がどうなっているかまだ調べてない。

## 気になっている点・迷っている点

- 外部APIの候補が複数ありそう（zipcloud / 日本郵便公式 / 有料サービス）。とりあえず無料で使えそうな zipcloud から調べる。無理そうなら他を検討。
- 該当住所が無かったときの挙動が読めない。エラー扱いにするのか、単に空のままにするのか。API側の仕様次第かもしれないので先に調査が要りそう。
- 取得した住所をDBに保存する必要があるか？ 要件的には「フォームに自動反映されればOK」に見えるので、多分保存は不要。ここは要確認だが、いったん「保存しない」前提で進めてよさそう。
- 実装をどこに置くか。既存の `ArticleService` 的な場所に混ぜるのは違う気がする。外部APIクライアントとして独立させたほうが筋が良さそう？ まだ確信はない。
- レート制限があるかどうか不明。あれば自前でキャッシュ or 制御が要るかも。無ければ都度呼び出しでよい。

## 次にやること

1. zipcloud のAPI仕様をWeb調査（エンドポイント、該当なし時のレスポンス、レート制限の有無）。
2. 既存コードに外部API呼び出しの類似実装が無いか軽くgrepで確認。
3. 上記がまとまったら [plan-writing.md](../../../guides/plan-writing.md) のフォーマットで詳細プランに整理する（調査ステップと実装ステップに分けるかは、調査が要ることが確定した時点で決める）。

## 書き方のポイント

- ラフプランは「まだ結論が出ていないこと」をそのまま書いてよい。箇条書きの粒度も揃える必要はなく、疑問形のまま残してもよい。
- 上記の調査観点・迷っている点は、実際に調査した結果 [01-research-zipcloud-api.md](../01-research-zipcloud-api.md) の「調査結果」に、採用した決定は [00-overview.md](../00-overview.md) の「主要な決定事項」に、それぞれ整理された形で反映されている。ラフプランはこの2ファイルの「下書き」にあたる。
- ラフプランの時点では「ルール更新ポイント」のような、詳細プランで必須の項目を埋める必要はない。決定していないことを無理に決めない。
- **frontmatterの`status`はラフプラン用の4値。** 詳細プラン側の6値とは別物（[rough-plan.md](../../../guides/rough-plan.md) 参照）。
