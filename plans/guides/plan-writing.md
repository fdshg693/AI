# プラン作成時

実装前に書く詳細プランのフォーマット。1機能 = 1サブフォルダ（または小さい機能なら1ファイル）。

## 書く内容（5点のみ）

実装詳細（コードスニペット、具体的なプロパティ定義・メソッド本体など）は書かない。書くのは次の5点だけ。

- **やること**（1〜数行）
- **触るファイル**（新規／変更、パス＋一言）
- **読むべきファイル・実行推奨Grep**（実装前に理解しておくべき既存コード。「何を確認するために読むのか」という観点ごと、優先度ごとにグルーピングする）
- **決定事項・注意点／落とし穴**（判断の理由、既存コードとの衝突、競合状態など事前に言語化できるリスク）
- **ルール更新ポイント**（プロジェクトのルール・規約の格納先に・いつ・何を追記するか。格納先はプロジェクトにより異なる — 既存の慣習に合わせる。新規ルールファイルを作る場合は、対象パスを決めるところまでプランに書く）

コードそのものは実装時に既存の類似ファイルを読んで導出すればよく、プランに書き切る必要はない。

5点に加えて、ステップごとに「進め方」（実行主体・TODO粒度）を1〜3行添える（[進め方とTODO化](#進め方とtodo化)）。

## 節構成（lint で検査）

5点と「進め方」は、ファイルの種類ごとに次の `##` 見出しで書く。見出しは前方一致で照合するので、`## 決定事項・注意点／落とし穴` のように後ろを補ってよい。この表が節名の正本で、`lint_plans.py` は同じ一覧を定数（`REQUIRED_SECTIONS`）で持つ。表を変えたら定数も更新する。

| ファイル | 必須の `##` 見出し |
| -------- | ------------------ |
| 概要 `00-overview.md` | `実装ステータス`（frontmatter 直後の最初の見出し）、`要件`、`実装ステップ`、`主要な決定事項`、`変更/新規ファイル一覧`、`ルール更新ポイント`、`進め方` |
| 実装ステップ `NN-*.md` | `やること`、`読むべきファイル`、`触るファイル`、`決定事項`、`ルール更新ポイント`、`進め方` |
| 調査ステップ `NN-*.md`（`## 調査観点` を持つステップ） | `やること`、`調査観点`、`調査結果`、`進め方` |
| 単一ファイル完結 `{plan-name}.md` | 実装ステップと同じ。`implementing-done` なら `完了記録` も |

lint がこの節構成を検査するのは `status` が `ready` 以降のファイルだけ（`planning-*` の間は書きかけでよい）。実行中に足す「実行中に判明した変更」「計画との差分」などの節は自由に追加してよい。

## frontmatter（OKF準拠）

プランファイルの先頭には、Open Knowledge Format (OKF) 準拠のYAML frontmatter（`type`必須、`status`推奨）を付ける。

```yaml
---
type: Plan # 概要ファイル・単一ファイル完結プランはこの値
status: planning-breakdown
---
```

```yaml
---
type: Plan Step # ステップファイル（01-*.md, 02-*.md 等）はこの値
status: implementing-in-progress
---
```

`status`はOKF本来の値（`draft`/`stable`/`deprecated`）ではなく、プランの進捗粒度に合わせた次の6値を使う。

| 値                         | 意味                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| `planning-research`        | プラン中。内容を確定させるための追加調査がまだ必要                      |
| `planning-breakdown`       | プラン中。調査は完了/不要だが、実装できる粒度への分割・詳細化がまだ必要 |
| `ready`                    | プラン確定。調査/実装の実行にはまだ着手していない                       |
| `implementing-started`     | 着手した直後。全体のごく一部にしか手を付けていない                      |
| `implementing-in-progress` | 実行が部分的に完了し、継続中                                            |
| `implementing-done`        | 完了                                                                    |

- 省略時のデフォルトは定義しない。書き始めた時点で`planning-research`か`planning-breakdown`のいずれかを明示する。
- 概要ファイル・単一ファイル完結プランの`status`は機能全体の代表ステータスを手動更新する。個々のステップの詳細な状態は各ステップファイル側のfrontmatterを見る（自動集計はしない）。複数ステップの概要には、frontmatter直下に「実装ステータス」節を置き、各ステップを`- [ ]`で列挙する。

### status の遷移基準

| 遷移                                              | 実装ステップ                                     | 調査ステップ                                                 |
| ------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| `planning-*` → `ready`                            | 5点が埋まり、プランレビューの指摘を反映した      | 調査観点（キーワード・確認したい事実）が確定した             |
| `ready` → `implementing-started`                  | 最初の「触るファイル」に手を付けた               | 調査を開始した（最初の検索・ファイル読み込み）               |
| `implementing-started` → `implementing-in-progress` | 「触るファイル」の2つ目以降に手を付けた          | 調査観点の一部について結果が出た                             |
| `implementing-in-progress` → `implementing-done`  | 全ファイルの変更と検証が終わった                 | 要約をプラン本文に書き、後続ステップのプラン本文へ反映した   |

- 調査ステップの`implementing-*`は「コード実装」ではなく「そのステップの作業（Web調査等）の実行」を指す。
- 概要の`status`は、最初のステップが`implementing-started`になったら`implementing-started`、1つ以上のステップが完了したら`implementing-in-progress`、全ステップ完了と完了記録の作成後に`implementing-done`にする。

### プランフォルダ間の依存関係

複数のプランに実行順・着手条件がある場合は、各プランの`00-overview.md`（単一ファイル完結ならそのプランファイル）のfrontmatterに次のキーを書く。`Plan Step`、`rough/`、`progress/`には書かない。

```yaml
order: 2/3
depends_on:
  - ../browser-task-delegation/00-overview.md # Step3（コアループ）まで完了していること
blocks:
  - ../delegation-integration/00-overview.md # 本プラン完了後に着手可
```

- `order`は、依存でつながるプラン群の予定順を`現在位置/総数`で表す。依存関係を持つプランでは必須だが、着手可否の正本ではない。
- `depends_on`は着手前に満たすべき先行プラン。各項目のコメントに必要なステップ番号または完了条件を書く。実行時は参照先のoverviewと該当ステップの`status`で確認する。
- `blocks`は後続プランへの逆方向の宣言。各`depends_on`には先行プラン側の`blocks`を、各`blocks`には後続プラン側の`depends_on`を必ず対応させる。
- パスは宣言元からの相対パスで、対象プランの`00-overview.md`または単一ファイル完結プランを指す。自己参照・循環参照・片側だけの宣言は禁止する。

## 初版の凍結スナップショット（`snapshot/`）

プランは実行中に更新するため、初版の状態が失われやすい。レビューを1周した後の実行着手前に、初版を `snapshot/` に凍結する。

- 取得はリポジトリルートで1回だけ実行する: `uv run plans/snapshot_plan.py plans/{plan-name}`（依存は標準ライブラリのみなので、導入先では `python` でもよい）。親フォルダ直下のプランファイル（`00-overview.md`、`01-*.md`…）を逐語コピーし、`snapshot/README.md` に取得日時と対象一覧を記録する。`rough/`・`progress/` はコピーしない。
- 取得後は `snapshot/` を一切編集しない。更新は常に親フォルダ側のプランだけに行う。
- 取得も取り直し（`--force`）も実行着手前に限る。`snapshot_plan.py` は overview の `status` が `planning-*`/`ready` 以外だと取得を拒否し、`--force` は常に拒否する。
- 初版との差分は、プランフォルダを cwd にして `git diff --no-index snapshot/00-overview.md 00-overview.md` のように比較して取る。
- この仕組みは `{plan-name}/` フォルダ方式のプランが対象。単一ファイル完結プランは元が短く `snapshot/` を置くフォルダを持たないため、「計画との差分」節で変更を残す。
- **単一ファイルからフォルダ方式へ移す手順**: 規模が膨らんだら、(1) `{plan-name}/` を作り、ファイルを `00-overview.md` として移す（必要ならステップファイルへ分割）、(2) まだ実行着手前なら通常どおり `snapshot/` を取る。実行開始後に移す場合は、移す直前の内容を初版相当とみなして `--allow-late` 付きで取得する（`snapshot/README.md` に「実行開始後に取得（初版ではない）」と自動で記録される）。元の「計画との差分」節は移行後も親側プランに引き継ぐ。

## 実行中の変更を残せる構成にする

初版は `snapshot/` に凍結されているので、親フォルダ側のプラン全体を自由に書き換えてよい（古い記述の削除・全面改稿を含む）。`snapshot/` は編集しない。次の形で、実行可能な状態と経緯を両立させる。

- 後続ステップに影響する事実は、対象となる後続ステップの「やること」「触るファイル」「決定事項」「注意点」へ直接反映する。progressを引継ぎ先にしない。
- 変更したステップには「実行中に判明した変更」または「計画との差分」節を追加し、判明時点・変更内容・更新した節を1〜2行で残すと変更点を追いやすい（初版との厳密な差分は `snapshot/` との比較で取れる）。
- 調査ログや変更理由の詳細だけをprogressへ分離する。後続の実装者が次に何をするかを判断するためにprogressを読む必要がある状態にしない。

## 整合性チェック（lint）

frontmatter・依存関係・チェックボックス・節構成の手動更新漏れを検出するため、同梱の `lint_plans.py` を使える（リポジトリルートで `uv run plans/lint_plans.py plans`。`python` でもよい）。`type`/`status` の値、`depends_on`/`blocks` の対応と循環、`order` の書式、overview のチェックボックス（リンク先のステップファイル）とステップ `status` の矛盾、[節構成](#節構成lint-で検査)、`implementing-*` のフォルダ方式プランの `snapshot/`、`implementing-done` の完了記録を確認する。問題は `path:line: メッセージ` の形式で出力され、エラーがあれば非0で終了する（`--strict` で警告も失敗扱い）。プランを更新したら、レビュー依頼前・完了前に実行する。

テンプレートのサンプル（`references/`。コピー先の `plans/` と同じ構造）を編集したときは `--examples` を付けて実行する（架空の兄弟プランへの参照を警告にとどめ、サンプルに置いていない `snapshot/` の検査を省く）。

## 外部知識が必要な場合: 事前調査ステップ

外部API・外部ライブラリなど、実装前にWeb上のドキュメントを確認しないと決定事項が固まらない機能では、調査を**独立した1ステップ**として先に切り出す。

- 関連しそうなキーワード・URLをまず洗い出し、取得・理解する。
- 調査結果は「要約 + 参照URL」として出力する。読んだページの全文は書かない。後続の実装ステップはこの出力を前提に書き、調査時の文脈を持ち込まない。
- 調査は無駄なページ取得も含めてコンテキストを多く消費するため、実装ステップと同じファイルに混ぜない。

## ステップ分割の目安

- 触るファイルが3〜4個以内で、既存レイヤーをまたぐ新規追加（新しいEntity/Repository/Serviceの新設など）がなく、独立した調査ステップも不要 → 単一ファイルで完結させる
- 新規ドメイン追加、複数レイヤーにまたがる、または外部API・外部ライブラリの事前調査が必要 → `00-overview.md` + ステップ分割ファイル群（`01-*.md`, `02-*.md`…）

## 進め方とTODO化

各ステップには、5点に加えて「進め方」節を1〜3行で書く。書かないと「誰が・どこまでを1作業単位として進めるか」が実行時の思いつきに委ねられ、作業の分割やTODOの粒度がぶれる。

- **実行主体**: メインのエージェントがそのまま進めるか、サブエージェント等に委任するか（使えるなら）。委任先には調査・作業だけをさせ、決定事項の採否はプランを書く側が行う。
- **TODO化**: どの単位で1つのTODOにするか（下記）。

使えるサブエージェント・スキルは導入先によって異なるため、具体名は `plans/AGENTS.md` の「導入先固有の運用」節に書く（Claude Code での例: [claude-code-execution.md](claude-code-execution.md)）。

各ステップは実行時にTODO（タスク）として追跡できる形に書く。

- **1セッションで完結する小機能**: ステップの「やること」1行をそのままチェックリストの1項目にする。
- **複数セッションをまたぐ・一時中断が前提の機能**: 現状・次にやることを残す軽量なメモ（`CURRENT.md`相当）を別途持たせ、プラン側のoverview実装ステータスチェックボックスと二重管理にならないよう棲み分ける。
- **他プランに依存する機能**: `depends_on`の各条件を先に確認するTODOを置く。条件未達なら実装TODOを開始せず、関係を変更する場合は相手の`blocks`/`depends_on`も同じ変更で更新する。

TODOの粒度は「1項目 = 1コミット/1レビュー単位」を基準にする。

詳しい実行時の進め方（進捗記録・後片付け）は [plan-execution.md](plan-execution.md) を参照。

## プランレビュー（サブエージェントに1回依頼する。必須）

プランは分量が多く、誤りが実装フェーズまで気づかれないと手戻りが大きい。詳細プランを書き終えたら（概要＋ステップ分割・単一ファイル完結いずれも）、実装に着手する前に**必ず1回**、サブエージェント機能（利用可能なら）にレビューを依頼する。

- レビュー→修正のサイクルは**1周のみ**。指摘を踏まえて修正したら、その修正に対する再レビューは不要（レビューをループさせない）。
- 依頼文テンプレート:

```
以下のプランをレビューしてください。実装はまだ着手していません。プラン自体の書き直しは不要で、指摘のみ返してください。

# 元の依頼
{ユーザーからの依頼の全文をここに貼る}

# プラン全文
{00-overview.md〜各ステップファイル、または単一ファイル完結プランの全文をここに貼る}

# 確認してほしい観点
- 「やること」と元の依頼の間にズレ・抜け漏れがないか
- 「触るファイル」に不足・誤りがないか（実在するパスか、他に触るべきファイルが漏れていないか）
- ステップ間およびプラン間の依存関係・実行順序に矛盾がないか（プラン間では`order`、`depends_on`、`blocks`の相互対応と着手条件を確認）
- 「決定事項・注意点」に書かれていない隠れたリスク（競合状態、既存コードとの衝突、破壊的変更など）がないか
- ルール更新ポイントの記載漏れ（新規/変更が必要なルールファイルとその格納先）

指摘は「致命的（実装前に必ず直すべき）」「軽微（直さなくても進められる）」に分けて簡潔に列挙してください。
```

レビュー指摘を踏まえて修正したら（修正に対する再レビューは不要）、実行着手前に [初版の凍結スナップショット](#初版の凍結スナップショットsnapshot) を取る。
