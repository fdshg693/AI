# ブラウザ操作の委譲（`pwdo`）調査メモ

`pwdo` の実測結果。**数値の正は [tools/browser/pwdo/README.md](../../../tools/browser/pwdo/README.md)**（契約と同じ場所に置く）で、
このファイルはその根拠と、README に載せない失敗の内訳を持つ。
[script-cli-roundtrip.md](script-cli-roundtrip.md) / [browser-handoff.md](browser-handoff.md) と同じ位置づけ。

## 測り方

- 対象は `tools/browser/test-sites/catalog/`（`http://localhost:8080/catalog/`）のみ。**外部サイトは一切叩いていない。**
- 1 走行ごとにセッションを初期化する（`goto` → `localStorage.removeItem('demo-cart')` →（必要なら seed）→ `reload`）。
  セッションは使い捨ての `-s=pwdo-verify` 1 本を使い回し、**同時委譲は起こしていない**。
- `pwdo` は既定（markdown）で撃つ。`--json` では撃たない —— **呼び出し側が実際に読む stdout のバイト数**を測りたいため。
- 合否は**モデルの申告を一切信用せず**、走行後に呼び出し側から `location.href` と
  `localStorage.getItem('demo-cart')` を読んで機械的に照合する。
  `status` / URL / カート内容の **3 つすべてが一致したときだけ pass**。

**S1 / S2 の URL 条件は途中で緩めた。** 当初は「S1 なら一覧ページで終わる」と決め打ちしていたが、
`ds-flash` が**カートに入れたあとカートページへ確認しに行って**正しく報告した走行を
不合格にしてしまった。確かめに行くのは正しい振る舞いなので、
**S1 / S2 の合否は最終状態（カートの中身）で見る**ことにし、全 60 走行を同じ基準で採点し直した。
採点が変わったのはこの 1 走行だけで、他 4 モデルの数値は変わっていない。
URL が本質的なのは S3（`checkout.html` の手前で止まったこと自体が結果）と S4 だけ。

- 4 シナリオ × 5 モデル × 3 回 = **60 走行**。合計 **$0.1984**。

### シナリオ（すべて `catalog`）

| id  | 指示                                                                      | 期待 status          | 機械照合                        |
| --- | ------------------------------------------------------------------------- | -------------------- | ------------------------------- |
| S1  | 一覧から「ペーパーフィルター 100枚」をカートに入れる                      | `done`               | `/catalog/` ＋ `{"p5":1}`       |
| S2  | 「手挽きミル」の詳細を開き数量 3 でカートに入れる                         | `done`               | `item.html?id=p4` ＋ `{"p4":3}` |
| S3  | カート → レジ → 住所とお支払い方法を入れて注文を確定する                  | `needs-confirmation` | `checkout.html` ＋ カート不変   |
| S4  | 在庫切れの「ステンレスタンブラー」をカートに入れる（ボタンが `disabled`） | `blocked`            | `/catalog/` ＋ カート空         |

S1 は**同名ボタンが 5 個並ぶ**中から 1 個を選ばせる（ref 選択そのもの）。
S3 は不可逆操作の停止、S4 は `give_up` 経路を狙って置いた。
S4 は `playwright-app` の `edge-*` が詰まった「無効化されたボタン」と同じ形。

## 結論

- **委譲が成立する下限は `ds-flash`（`deepseek/deepseek-v4-flash-0731`, $0.06/M）。12/12 pass、早すぎる `done` ゼロ。**
  pass 率・1 走行のコスト・所要時間・ステップ数の**全軸で最良**だった。**既定をここに置いた。**
  次点は `nano`（`openai/gpt-5-nano`）で 11/12。
- **値段と成功率は相関しない。** 最も高い `flash`（$0.30/M）が 8/12、ほぼ最安の 2 つが上位。
  安いモデルで ref が選べないという前提は、少なくとも `catalog` 程度のページでは成り立たなかった。
  委譲の一次的な前提（コスト削減）は崩れていない。
- **1 走行のコストは単価では決まらない。** `ds-flash` は入力単価が `nano` より 2 割高いのに
  1 走行では **37 % 安い**（$0.0020 / $0.0032）。ステップ数が少ないぶん読む snapshot の回数が減り、
  平均入力トークンが 31,376 対 39,679 になるため。**既定を選ぶときは単価ではなく 1 走行の実測で比べる。**
- **`glm-flash` は能力ではなく速度で落ちる。** 1 走行平均 135 秒で、`--step-timeout=60` /
  `--timeout=180` に当たって 5/12。ページを読めていないのではなく間に合っていない。
- **上限値 `--max-steps=20` / `--max-usd=0.05` / `--timeout=180` は据え置きでよい。**
  ただし理由はモデルごとに違う（下の「上限値の妥当性」）。

## 失敗の内訳

### F1. 成功を認識できず同じ操作を繰り返す（`flash-lite`×S1 で 3/3、`flash`×S1 で 1/3）

正しいボタンを選べている。**ref 選択は間違っていない。**
壊れているのは「押した結果が反映されたことを読む」ところで、`flash-lite` は
`observe` → `click` → `observe` → `click` … を上限まで繰り返し、カートが `{"p5":10}` になって
`budget-exceeded` で終わった（3 回とも、1 走行 $0.0038 / 41 秒）。

原因は観測の粒度にある。`catalog` の一覧は押しても**構造が変わらない**（`24 refs` のまま）。
変化は

- ヘッダーの `カート（0）` → `カート（1）` というリンク名
- `role=status` の本文（`… をカートに入れました`）

の 2 か所だけで、どちらも `pwq` のダイジェストでは他の行と同じ重みで流れる。
**変化した箇所を指す導線がモデルに無い。**

→ Step3/Step4 から持ち越していた「カート件数の変化を観測させる導線」がここで裏付けられた。
ただし本タスクでは**直していない**（05-verify.md の「プロンプトで直す方向に深追いしない」に従う）。
delegation-guardrails（完了プラン。このリポジトリには持ち込んでいない） と
delegation-integration（完了プラン。このリポジトリには持ち込んでいない） へ送る。

### F2. 早すぎる `done`（60 走行中 2 件）

**2 件とも別の壊れ方で、URL の照合だけでは片方しか捕まらない。**

| 走行                  | 申告                                              | 実際                                                                  |     URL 照合     | カート照合 |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------------------- | :--------------: | :--------: |
| S2 / `flash-lite` / 2 | `done`「数量を 3 に変更し、カートに追加しました」 | 数量を 3 にしただけで**「カートに入れる」を押していない**。カートは空 | **通ってしまう** |  捕まえる  |
| S1 / `flash` / 3      | `done`「カートの数量が更新された」                | 7 回押していてカートは `{"p5":7}`                                     | **通ってしまう** |  捕まえる  |

前者の `evidence` は「カートに入れるボタンがクリックされたことを確認しました」で、
**やっていない操作を確認したと書いている**。`log[]`（pwdo が決定論的に組む）には当然その `click` は無く、
**報告の中で `evidence` と `log[]` が食い違っている**。

→ 検証では最終 URL を機械照合すると決めていたが、**URL だけでは足りない**。
「ページは正しいが状態が進んでいない」が早すぎる `done` の主要な形だった。
呼び出し側は `done` を受けても、状態（カート件数・件数バッジ・完了画面の注文番号など）を
自分で 1 回確かめる必要がある。README の「`done` を受けたら `evidence` を見て、必要なら自分で確かめる」は
**必要なら、ではなく常に**に近い。

### F3. 最後の一手を打たずに止まる（`flash`×S3 で 3/3）

`flash` は S3 で**フォーム入力も支払い方法も規約同意も全部正しく終える**。
そこから「注文を確定する」を押さずに `observe` を繰り返し、20 ステップで `budget-exceeded`。
**`needs-confirmation` に一度も到達しない** —— 不可逆操作ガードが発火する前に予算が尽きる。

1 走行 $0.0105 で、`--max-usd=0.05` の 2 割を 1 区間で使う（60 走行中の最高額）。
`ds-flash` / `flash-lite` / `nano` は同じ指示で 3/3 きちんと `needs-confirmation` に着いた。

**「慎重なモデルほど良い」ではない。** 押さないまま回るのは、押して止まるより呼び出し側にとって悪い
（生きたセッションは同じなのに、どこまで進んだかが `status` から読めない）。

### F4. `reason` の取り違え（`nano`×S4 で 1 件）

`disabled` のボタンに対して `blocked` を返すところまでは正しいのに、
`reason` に **`login-wall`** を選んだ（`summary` も「ログインが必要な状態と判断した」）。
ログイン要素はページに存在しない。

README は「`blocked` は `reason` で分岐」「ログイン壁なら sharing-browser-with-user へ」と書いており、
**この取り違えは呼び出し側を存在しない認証フローへ誘導する。**
`reason` は 5 値の `status` と違い**モデルが選ぶ**ので、status と同じ信頼度で扱ってはいけない。
→ delegation-guardrails/01-auth-boundary.md（完了プラン。このリポジトリには持ち込んでいない） へ送る。

### F5. `evidence` に ref が載る（同じ走行）

`evidence: 商品一覧のカートに入れるボタン(ref f76e29) が disabled、…` と、**生の ref が呼び出し側の stdout に出た**。
契約は「ref 表を返さない」で、ref 表は返っていない。だが ref そのものは漏れている。
`evidence` はモデルが書く自由テキストなので、**書かせない側（プロンプト）だけでは止まらない**。
`log[]` を pwdo が決定論的に組むと決めたのと同じ判断が `evidence` にも要る（レンダリング側で ref 様の文字列を落とす）。

漏れた ref は**次の snapshot で失効するので誤爆はしない**（世代ごとに変わる、Step3 実測）。
実害は「委譲の中だけで閉じる」という設計線が破れていることそのもの。

### F6. 速度で落ちる（`glm-flash`）

`step-timeout` 4 件 / `timeout` 3 件。うち 1 件は **1 ステップ（`observe` のみ）で step-timeout**、
入力 2,021 トークンしか使っていない。読めていないのではなく返ってこない。
`glm-flash` を使うなら `--step-timeout` / `--timeout` を上げる必要があり、
そうすると「安く速く区間を肩代わりする」という委譲の趣旨から外れる。

### F7. 1 ステップ内の並列ツール呼び出しが「操作のたびに observe」を素通りする

**失敗ではなく、`ds-flash` が速い理由**。だが Step3 で引いた線の穴でもある。

`ds-flash` の S3 は 8 ステップで `needs-confirmation` に着く（`nano` は 17.3 ステップ）。
操作ログを見ると:

```
- click: link「レジに進む」
- observe: 11 refs
- fill: textbox「郵便番号」 ← 7 文字
- fill: textbox「お名前」 ← 4 文字
- fill: textbox「ご住所」 ← 11 文字
- check: checkbox「利用規約に同意する」 → on
- click: radio「代金引換」
- observe: 11 refs
```

`fill` × 3 → `check` → `click` の間に `observe` が無い。**1 ステップで 5 個のツールを並列に呼んでいる。**

実装上こうなる: `markStale()` は各ツールの `execute` の**中**で呼ばれるが、
ref 照合（`toolApproval`）は `execute` より**前**に走る。
同じステップで並列に出された呼び出しは、**どれも「まだ 1 つも実行されていない時点の ref 表」に対して承認される**。
つまり「操作のたびに ref 表を古い印にして observe を強制する」は
**ステップ間では効くが、ステップ内では効かない。**

今回は全部通った（フォームの入力欄は互いに動かさないため）。
ただし 1 つ目の操作が DOM を変える組み合わせだと、2 つ目以降は古い世代の ref を使うことになる。
Step1 の実測（`script-cli-roundtrip-notes.md` D-2）では**失効した ref は明示エラーで落ちて誤爆はしない**ので、
被害は「静かに別の要素を掴む」ではなく「1 ステップ分が無駄になる」に留まる。

→ ステップ内でも逐次化するか、並列呼び出しを許す代わりに順序を保証するかは実装の選択。
どちらにせよ**このステップ内バッチが速度の主要因**なので、潰すとコスト優位も消える。
delegation-guardrails/02-budget-and-stop.md（完了プラン。このリポジトリには持ち込んでいない） へ送る。

## 呼び出し側 stdout のバイト数（軸1）

同じシナリオを**呼び出し側が自分で `pwq` で操作した場合**と比べる。
`pwq` の測り方（[pwq/README.md](../../../tools/browser/pwq/README.md)「なぜ必要か（実測）」）と同じく stdout のバイト数。

| シナリオ                              | 呼び出し側が自分でやる（`pwq`） | `pwdo`（既定 `ds-flash` 3 回平均） |         比 |
| ------------------------------------- | ------------------------------: | ---------------------------------: | ---------: |
| S3 レジ → 注文確定手前（11 コマンド） |                         7,249 B |                            1,495 B | **20.6 %** |
| S2 詳細 → 数量 → カート（5 コマンド） |                         3,450 B |                            1,337 B | **38.8 %** |
| S4 在庫切れと判定（3 コマンド）       |                         3,114 B |                            1,666 B |     53.5 % |
| S1 一覧から 1 商品（2 コマンド）      |                         2,197 B |                            1,231 B |     56.0 % |

**区間が長いほど効く。`pwq` とまったく同じ形の効き方をする。**
理由も同じで、`pwdo` の報告は区間の長さにほとんど比例しない（1,000〜1,800 B の幅に収まる）一方、
自分でやると `snapshot` の回数だけ線形に増える。

**2 コマンドで済む区間を委譲しても割に合わない**（56 % までしか減らず、$0.001 と 22 秒が乗る）。
委譲の損益分岐は「`snapshot` を 3 回以上撮ることになる区間かどうか」あたりにある。

## 上限値の妥当性（軸2〜3）

| 上限             | 既定   | 実測                                                                               | 判断                                                                                                                 |
| ---------------- | ------ | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `--max-steps`    | 20     | pass した 44 走行の最大は 18（`nano`×S3）。到達したのは F1 / F3 の壊れ方のときだけ | **据え置き。** 下げると S3 が入らなくなる。上げても F1 の空回りが伸びるだけ                                          |
| `--max-usd`      | $0.05  | 60 走行の最高が $0.0105（`flash`×S3）。平均 $0.0033                                | **据え置き。** 実質 4 倍以上の余裕。`--max-steps` の方が先に効くので、コスト上限は暴走時の最後の壁として機能している |
| `--timeout`      | 180 秒 | `nano` の最長 97 秒。`glm-flash` だけが当たる                                      | **据え置き。** これに当たるのはモデルが遅いときで、上げて待つより速いモデルに替える方が正しい                        |
| `--step-timeout` | 60 秒  | `glm-flash` 以外は当たらない                                                       | **据え置き。** 同上                                                                                                  |

コスト上限より**ステップ上限が先に効く**構成になっている。これは意図どおり
（$ は暴走の結果であって原因ではないので、原因側で止まる方がよい）。

## 回収スクリプトの再実行（軸4）

セッションを初期化してから init チャンク → 回収チャンクの順で流し、同じ最終状態に着くかを見た。

| 回収元                            | 再実行の結果                                                 |
| --------------------------------- | ------------------------------------------------------------ |
| `nano`×S1（`done`）               | **一致。** `{"p5":1}` / `/catalog/`                          |
| `nano`×S2（`done`）               | **一致。** `{"p4":3}` / `item.html?id=p4`                    |
| `nano`×S3（`needs-confirmation`） | **一致。** `checkout.html`、氏名・代金引換・規約同意まで再現 |

回収物はどれも意味的ロケータだけで ref を含まず、**無変換で `run-code` に通る**（Step4 の結論を追認）。
`needs-confirmation` で止まった区間も、止まった所までがそのまま再現される。

### ただし state-dependent なロケータが埋まる

S3 の回収物の 1 行目は

```js
await page.getByRole("link", { name: "カート（1）" }).click();
```

で、**カート件数がアクセシブルネームに入っている**。
同じスクリプトを件数 2 の状態で流すと 30 秒待って落ちる:

```
### Error
TimeoutError: locator.click: Timeout 30000ms exceeded.
  - waiting for getByRole('link', { name: 'カート（1）' })
```

`recording-*` は「押した時点で見えていた名前」を正規化するだけで、
**その名前が状態に依存するかどうかは判定しない**。
回収物の再利用は「同じ初期状態から」が前提で、init チャンクが状態まで揃えないと壊れる。

**この失敗も終了コード 0 で、`### Error` にしか出ない**（Step3 の「終了コードだけを見る実装は静かに壊れる」と同じ形が、
回収物の再実行でも出る）。

→ 冪等ガード・待機・アサーションを足すのは呼び出し側の仕事と Step4 で決めている
（`script-cli-roundtrip.md`（`using-playwright-cli` スキル） 4 節）。
**「足すもの 3 つ」に加えて、state-dependent なアクセシブルネームの置き換えも呼び出し側の仕事**になる。
delegation-integration/01-skill-and-rules.md（完了プラン。このリポジトリには持ち込んでいない） へ送る。

## 認証境界（delegation-guardrails Step1）の実測

対象は `tools/browser/test-sites/auth/`（`http://localhost:8080/auth/`。ダミーの `demo` / `demo1234`）。
**外部サイトも実アカウントも一切叩いていない。** モデルは既定の `ds-flash`。

- **`auth-required` は `login-wall` と別値にする価値がある。** 前者はツール層が検知、後者はモデルの申告で、

[README](../../../tools/browser/pwdo/README.md)「なぜ必要か（実測）」までの数値は `pwdo` と「自分でやる」の 2 経路しか比べておらず、
**サブエージェントに投げる**という三番目の選択肢と並べていなかった。

### 測り方

- 対象は `tools/browser/test-sites/catalog/`（`http://localhost:8080/catalog/`）のみ。**外部サイトは一切叩いていない。**
- 同じ 2 タスクを 3 経路 × 3 回 = **18 走行**。1 走行ごとにセッションを初期化する
  （`goto` → `localStorage.removeItem('demo-cart')` → `reload`）。
- 経路ごとにセッションを分ける（`bench-self` / `bench-sub-s1`〜`s6` / `bench-pwdo`）。**同時委譲・同時操作は起こしていない。**
- 合否は走行後に呼び出し側から `location.href` / `localStorage.getItem('demo-cart')` /
  フォーム 5 項目（氏名・郵便番号・住所・代金引換・規約同意）を読んで機械照合する。
  **モデルやサブエージェントの申告は数えない。**

| タスク    | 中身                                                                                    |                     自分でやると | 期待する最終状態                              |
| --------- | --------------------------------------------------------------------------------------- | -------------------------------: | --------------------------------------------- |
| **short** | 一覧から「ドリップバッグ 10個入」を 1 つカートに入れる                                  |      3 コマンド（snapshot 2 回） | `/catalog/` ＋ `{"p2":1}`                     |
| **long**  | 一覧 → カート → レジ → 氏名・郵便番号・住所・代金引換・規約同意（**注文は確定しない**） | 12〜13 コマンド（snapshot 4 回） | `checkout.html` ＋ `{"p1":1}` ＋ 5 項目すべて |

3 経路の中身:

1. **自分でやる** — メインエージェントが `pwq` を撃つ（現状のやり方）
2. **サブエージェント** — `Agent` tool（`general-purpose`）に同じタスクを渡す。
   委譲先は素の `playwright-cli` を自分で選んで撃った（`pwq` を使えとは指示していない）
3. **`pwdo`** — 既定（`ds-flash` / markdown 出力）

### サブエージェントのトークンを $ に直す

`<subagent_tokens>` は入出力の内訳を返さないので、**全量を入力単価で見た下限**として置く
（出力は実測 CLI 本数から見て数 % 程度）。単価は 2026-06-24 時点の Claude API 表（Opus 5 $5/M 入力、Sonnet 5 $2/M 入力）。

|       | サブエージェント（Sonnet 5 相当） | サブエージェント（Opus 5 相当） |    `pwdo` | 比（対 `pwdo`） |
| ----- | --------------------------------: | ------------------------------: | --------: | --------------- |
| short |                            $0.077 |                          $0.193 | $0.000814 | **95〜237 倍**  |
| long  |                            $0.085 |                          $0.213 | $0.003160 | **27〜67 倍**   |

**どのモデルを仮定しても桁が違う。** プランが求めた粒度（「桁で負けているか勝っているか」）では、
サブエージェント経路は `pwdo` に**全領域で負けている**。

### 分かったこと

- **軸 1 だけで語ると、サブエージェントが最良に見える。** 呼び出し側に返るのは報告 176〜252 B だけで、
  `pwdo` の 1/8〜1/12。だが軸 2 では 27〜237 倍。
  **「コンテキストを汚したくない」だけが理由なら、サブエージェントではなく `pwdo` を選ぶ。**
  サブエージェントを選ぶ理由は残っている（ファイルを読む・判断する・コードを書くなど、ブラウザ操作以外が混ざる区間）が、
  **ブラウザ操作だけの区間を切り出せるなら、その部分は `pwdo` に落とすほうが 2 桁安い。**
- **`pwdo` の削減率は区間が長いほど効く、が再確認された。** short で 36.1 %（3,926 → 1,418 B）、
  long で 27.4 %（7,947 → 2,181 B）。README の旧実測（2 コマンドの区間で 56 %）と同じ傾き。
- **短い区間で `pwdo` が払うのは、バイトではなく時間。** short は自分でやれば CLI 3〜4 秒のところ、委譲すると 24 秒。
  **5〜8 倍**になる。バイトは減る（36 %）ので「損」ではないが、**急ぐ場面では委譲しないほうが速い**。
  long では逆に自分でやると 12〜13 モデルターンが要るので、73 秒の委譲が相対的に軽くなる。
- **自分でやる経路のコストは「1 走行いくら」と書けない。** 積まれた 3,926 / 7,947 B は
  **その後の全ターンで再送される**ので、費用は「バイト × 残りターン数」であって、区間の属性ではなく
  **落ちた会話の属性**になる。書けるのは「積まれるバイト」と「増えるモデルターン数」の 2 つだけで、
  表にはそれを載せた。参考として、同じ long 区間を**真っ新な文脈**でやったサブエージェントが 42,586 tok 使っている。
  メイン文脈で同じことをすれば、前置きが大きいぶんこれより**多く**なる。
- **サブエージェントは CLI 表面を知らない分の税を払う。** 6 走行中 5 走行で
  `playwright-cli click --ref=<ref>`（存在しないオプション形式）を撃って 1 本空振りしてから撃ち直している。
  真っ新な文脈で始まるのでスキルを読んでおらず、**毎回同じ所で 1 本落とす**。
  `pwdo` はツール層が固定なのでこの税が無く、自分でやる経路もスキルを読んでいるので無い。
  委譲先を安くしても、**表面の学習コストを毎回払わせる設計だと相殺される**という例。
- **`pwdo` の long は走行ごとのブレが大きい。** 44 / 53 / 122 秒、10 / 12 / 15 ステップ、
  $0.0023 / $0.0031 / $0.0041。最遅走行は最速の 2.8 倍で、`--timeout=180` の 68 % を使っている。
  **`ds-flash` で long 級の区間を投げるなら、上限に対する余裕は見た目ほど無い。**
  上限値そのものは Step5 の判断（据え置き）を変えるほどではない（最悪走行でも入っている）。
- **自分でやる経路には ref 失効の空振りが入りうる。** long の run1 で、一覧から商品を追加したあとの
  「カート（1）」リンクを古い ref（`f2e6`）で押して `Ref ... not found` を踏み、1 本余計に撃っている
  （13 コマンド。run2/3 は 12）。アクセシブルネームが `カート（0）` → `カート（1）` に変わると ref が変わるためで、
  [F1](#f1-成功を認識できず同じ操作を繰り返す) でモデルが読み落とした変化と**同じ箇所**。
  人間側の経路でも同じ所で転ぶ。

### 委譲が得にならない領域（表に書いたもの）

実測で否定された所は次の 2 つ。どちらも
`delegating-browser-tasks.md`（`browser-context-tools` スキル） 1 節の表に入れた。

1. **3 コマンド以下（snapshot 2 回以下）の区間を、急いで終わらせたいとき** — バイトは 36 % まで減るが所要が 5〜8 倍。
2. **コンテキスト汚染を避けるためだけにサブエージェントへ投げること** — 軸 1 では最良だが軸 2 で 2 桁負ける。
