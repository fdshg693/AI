## 決定事項・注意点／落とし穴

| 決定                                                                                                                                                                                                                                            | 理由                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 分割方針: 同じファイル・モジュールを触る一連の作業は同じ`branch:<slug>`＋`depends_on`チェーンで直列化する。互いに独立したファイル・モジュールを触る作業は別ブランチに分けて並行実装を許す                                                       | 同一ブランチに直列化する目的はマージコンフリクト回避（並行編集を避けたいものだけ直列化すればよい）。無条件に全issueを1本のブランチに直列化すると並行実行のメリットが失われる |
| `group`（Linear Project）は依頼された機能・イニシアチブ単位で1つに揃える。1グループの中に複数の独立ブランチが並存してよい（グループ＝可視化の単位、ブランチ＝実装の単位で別軸）                                                                 | ユーザー要件の「タスクグループ」は人間が確認する単位（機能単位）であり、ブランチ分割（並行実装のための技術的な単位）とは別の関心事。1:1に固定すると柔軟性が失われる          |
| 新規に作成したissue群は、作成直後は`.linear-cli/config.json`の`project`をまだそのグループ名に切り替えない（＝デフォルトでは非アクティブのTodoとして積むだけ）。アクティブ化はユーザーの明示指示があったときのみ行う                             | 既存issueの処理中に誤って将来グループのissueを先取りしてしまう事故を防ぐ。[00-overview.md](00-overview.md)の「Project+config」方式の安全設計の要                             |
| issue作成後、依存関係グラフ（どれがどれに依存し、どれが同じブランチか）をユーザーへ要約報告し、`project`切り替え（アクティブ化）前にレビューを促す                                                                                              | 依存関係・ブランチ割り当ての誤りは後工程（実装中）で気づくとやり直しコストが高いため、配置直後に人間の目で確認できるようにする                                               |
| セルフチェック項目を手順書に明記する: `depends_on`の循環が無いこと／全issueに`branch`が設定されていること／同一ブランチ内で`depends_on`チェーンが分岐・合流せず一直線であること（v1では単純な直列のみサポートし、fan-in/fan-outは対象外と明記） | 循環依存や複雑なDAGを許すとStep4のclaim時判定ロジックが複雑化する。v1はユーザー要件（順番に実装できればよい）を満たす最小構成に絞る                                          |
