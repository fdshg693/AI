# Step 9(実験): 実ログに基づく抽出スクリプトのニーズ洗い出し

> [08-write-testing.md](08-write-testing.md) の続き。このステップはスクリプトを実装しない。Step1・3・7で得られた実ログを手作業で読み、`scripts/extract_log.py`に本当に必要な機能を洗い出して [10-implement-and-verify-extract-script.md](10-implement-and-verify-extract-script.md) に引き渡す。

> Step5のOTelデータはこの対象に含めない。OTelはStep5/6で専用のローカル収集基盤（`otel-stack/`）と専用クエリスクリプト（`scripts/query_otel_logs.py`）を別途持つため、汎用抽出スクリプトである`extract_log.py`の対象からは外す（[00-overview.md](00-overview.md)決定事項）。

## やること

ここまでの実験ステップで実際に手に入っているログ（セッショントランスクリプトjsonl、Step3のhookログ、Step7の`--debug-file`出力）を、抽出スクリプト無しであえて手作業（Read/Grepツールでの直接閲覧）で読んでみて、「何が探しにくいか」「どんな条件で絞り込めれば楽になるか」を実際に体験する。これによって、事前に想像で決めるのではなく、実データに基づいてスクリプトの機能要件を確定する。

## 検証観点・仮説

- セッショントランスクリプトjsonl — ファイルサイズと1行あたりの情報量を確認し、単純な`grep`だけで特定ツール呼び出しを追えるか、それとも「直近N件」「特定`tool_name`のみ」「時刻範囲」のような絞り込みが要るか
- Step3のhookログ — 追記式jsonlが実際にどれくらいの速度で肥大化するか、tail的な使い方（直近N件）で十分か
- Step7の`--debug-file`出力 — カテゴリ（api/hooks/mcp等）混在の生ログから、特定カテゴリ・特定キーワードだけを抜き出すのに何が要るか
- 抽出後の要約への渡しやすさ — 手作業で抜き出した断片をそのまま`aim` CLI（`aim-cli`スキル）に渡してみて、要約の質に影響する「渡し方」（JSON生のままか、整形したテキストか）の当たりをつける

## 検証の進め方（安全な実行方法・後片付け）

- 新規の副作用のあるコマンド実行は不要（Step1・3・7で既に得ている実データを読むだけ）
- 手作業での抽出に使った一時的なgrepコマンド・出力は、機能要件の裏付けとして記録に残す以外は破棄してよい

## 検証結果メモ（実施済み）

対象データ: セッショントランスクリプトは `%USERPROFILE%\.claude\projects\c--CodeRoot-AI\*.jsonl`（実在する複数ファイルで217行〜800行超、ファイルサイズ56KB〜1MB超まで幅がある）。hookログはStep3実施時の生ファイル自体は検証後に破棄済みだったため、代わりにStep7で保持されている `hook-fired.A2.jsonl`（同一のPreToolUse stdin JSON形式）を代用。`--debug-file`出力はStep7の4ファイル（計1576行）と`~/.claude/debug/*.txt`（自動生成分）。手作業はReadツール・Grepツール・Pythonワンライナー（`json.loads`で構造確認）で実施し、副作用のあるコマンドは実行していない。

### セッショントランスクリプトjsonl — 「困った場面」と欲しかった絞り込み条件

- 217行のファイルで`type`別件数を数えると `mode:17, file-history-snapshot:3, user:57, system:3, attachment:20, ai-title:17, assistant:81, last-prompt:16, file-history-delta:3` と、本体（`user`/`assistant`）以外のノイズ行が約3割を占めた。**`type`によるフィルタが最初に欲しい絞り込み条件**
- `assistant`行の`message.content`内`tool_use`ブロックの`name`を集計すると`Read:16, Grep:7, Bash:7, Glob:7, Write:4, Edit:5, Skill:3, ToolSearch:1`のように偏りがあり、「特定ツール呼び出しだけ追いたい」という場面で**`tool_use.name`（値の完全一致）によるフィルタ**が必要
- 全行に`timestamp`（ISO8601, `Z`付きUTC）が存在することを確認 → **時刻範囲フィルタが可能**
- **最大の詰まりポイント**: 1行が143,323文字（約140KB）に達する行が実在した（Readツールの結果がそのまま`toolUseResult`に埋め込まれるケース）。該当行をそのまま出力・`aim`に渡すと抽出結果自体が肥大化し、要約対象として不適切。**抽出結果は1行あたりの文字数を既定で切り詰め、必要なら全文表示できるオプションが要る**
- `isSidechain`フィールドでサブエージェント発言か判別可能（Step7の「サブエージェントは親セッションのhook/settingsを共有する」という知見の裏取りにも使える軸）
- キーワード検索は「行の生テキストへの部分一致」で十分（jsonlは1エントリ1行のため、ネストされた`text`/`tool_input`/`tool_result`の中身も同一行内にあり、JSONパース無しのgrepでも見つかる）

### hookログ（Step3相当、Step7の`hook-fired.A2.jsonl`で代用確認） — 欲しかった絞り込み条件

- スキーマは`hook_event_name`/`tool_name`/`tool_input`/`session_id`/`transcript_path`/`cwd`/`tool_use_id`等で、Step3の検証結果メモと一致
- **重要な発見**: `hooks-logging.md`（Step4成果物）に載っている実際のログ仕込みテンプレート（`log_stdin.py`）はstdinのJSONを**そのまま**追記するだけで、独自の`timestamp`フィールドを一切付与していない。そのため**hookログには時刻範囲フィルタが使えず**、絞り込みは実質「末尾から直近N件」（追記順=ファイル内の行順）が主軸になる
- 1行あたりのサイズはトランスクリプトほど巨大にならない（`tool_input`の中身次第だが数百バイト〜数KB程度）ため、直近N件でも実用上十分
- `tool_name`・`hook_event_name`での完全一致フィルタが有効な絞り込み軸

### `--debug-file`出力（Step7実データ、計1576行） — 欲しかった絞り込み条件

- フォーマットは構造化JSONではなく `<ISO8601タイムスタンプ> [LEVEL] メッセージ本文` のプレーンテキスト行。行頭のISO8601タイムスタンプで**時刻範囲フィルタが可能**（正規表現で行頭を切り出せる）
- Step1で確認済みの「`-d "hooks"`のようなカテゴリフィルタはClaude Code側では期待通り機能しない」という知見と整合し、メッセージ本文中に`[init]`/`[STARTUP]`/`[claudeai-mcp]`/`[ToolSearch:optimistic]`のような角括弧タグが**一貫した規約なしに**現れる（全行にあるわけではない）。**構造化された「カテゴリ」フィールドとして扱うのは無理があり、キーワード（正規表現）によるgrepとして設計するのが現実的**
- 実際に原因切り分けに使ったキーワードは`safe mode`/`Watching for changes`/`API error`等で、`grep -n`相当（行番号付き部分一致、大小無視オプションがあると尚良い）で十分だった。複数ファイル（A/A2/B/D）を横断して同じキーワードを探す場面があったため、**複数ファイルパスをまとめて対象にできると楽**

### `aim` CLIへの渡し方の当たり

- 抽出結果を生JSON（特に上記の140KB行のような巨大な1行）のままプロンプトに渡すのは要約の質・トークン消費の両面で不利。**抽出時点で「どのファイルの何行目・どんな種別か」というヘッダー行を付けてテキスト化してから渡す**方が読みやすい
- 複数の抽出結果（例: hookログの数件＋トランスクリプトの数件）をまとめて1回の要約対象にしたい場面があるため、**抽出スクリプトの出力は1回の実行で1つのファイルにまとめて書き出し**、そのファイルパスをそのまま`aim`（`--prompt "$(cat <path>)"`またはstdinパイプ）に渡せる形にする

### Step10への申し送り（機能要件まとめ）

1. 対象ログ種別を切り替えられること（トランスクリプト＝JSON1行、hookログ＝JSON1行、debug-file＝プレーンテキスト1行、で内部パーサが異なる）
2. トランスクリプト・debug-fileは時刻範囲（`--since`/`--until`）でフィルタできること。**hookログは時刻範囲フィルタの対象外**（フィールドが存在しないため）と明記する
3. トランスクリプトは`--type`（user/assistant等）・`--tool`（tool_use名の完全一致）でフィルタできること
4. hookログ・debug-fileは「末尾から直近N件/N行」で絞り込めること
5. 全種別共通でキーワード（部分一致、正規表現・大小無視オプション）フィルタがあること
6. 出力1件あたりの文字数を既定で切り詰め、`--full`相当のオプションで全文表示できること（140KB行対策）
7. 複数ファイル（同一種別）をまとめて対象にできること
8. 出力は「どのファイルの何行目・どんな種別か」のヘッダー付きテキストとして1つのファイルにまとめて書き出し、書き出したパスを標準出力に明示すること（`claude-code-docs/extract_doc_section.py`の`output/temp/`パターンを踏襲）
