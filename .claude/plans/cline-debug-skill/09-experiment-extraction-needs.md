# Step 9(実験): 実ログに基づく抽出スクリプトのニーズ洗い出し

> [08-write-testing.md](08-write-testing.md) の続き。このステップはスクリプトを実装しない。Step1・3・7で得られた実ログを手作業で読み、`scripts/extract_log.py` に本当に必要な機能を洗い出して [10-implement-and-verify-extract-script.md](10-implement-and-verify-extract-script.md) に引き渡す。

> Step5のOTelデータはこの対象に含めない。OTelは既存の収集基盤（`otel-stack/` + `query_otel_logs.py`）側の担当のため、汎用抽出スクリプトである `extract_log.py` の対象からは外す（[00-overview.md](00-overview.md)決定事項）。

## やること

ここまでの実験ステップで実際に手に入っているログ（`~/.cline/data/logs/` の `cline.log`・`hub-daemon.log`・`hooks.jsonl`、`sessions/<id>/` のセッションJSON、Step7の `--json` 出力、VSCode拡張側の `tasks/<id>/` 配下）を、抽出スクリプト無しであえて手作業（Read/Grepツールでの直接閲覧）で読んでみて、「何が探しにくいか」「どんな条件で絞り込めれば楽になるか」を実際に体験する。これによって、事前に想像で決めるのではなく、実データに基づいてスクリプトの機能要件を確定する。

## 検証観点・仮説

- `cline.log`（約8.8MB）・`hub-daemon.log`（約199MB）— フォーマット（プレーンテキストかJSON行か、タイムスタンプ形式、レベル表記）の確認と、**巨大ファイルの扱い**。199MB級のファイルは全文読み込みが現実的でないため、「直近N件」「時刻範囲」での絞り込みが必須になるはず。実際に困るサイズ感を確認する
- `hooks.jsonl` — 1行1JSONの構造（`ts` / `hookName` / `sessionId` 等。Step1・3で確認済みのはず）で、`ts` があるため時刻範囲フィルタが可能か。`hookName` や `sessionId` での絞り込みの実用性
- セッションJSON（`<id>.json` / `<id>.messages.json`）— 構造（1行1JSONか整形済みJSONか）と肥大化の実態。Claude Code版で実測された「1行が140KB級になる巨大行」相当が存在するか。ツール呼び出しの表現方法（特定ツールだけ追いたい場合の絞り込み軸）
- `--json` 出力（Step7で取得）— 構造と、ファイルログとの重複／相補関係（同じ情報がどちらにもあるか、`--json` でしか取れないものは何か）
- VSCode拡張側 `tasks/<id>/` 配下 — ファイル形式と、CLI側のセッションJSONとの対応関係。抽出対象として別種別が必要か
- 抽出後の要約への渡しやすさ — 手作業で抜き出した断片をそのまま `aim` CLI（`aim-cli` スキル）に渡してみて、要約の質に影響する「渡し方」（JSON生のままか、整形したテキストか）の当たりをつける

## 検証の進め方（安全な実行方法・後片付け）

- 新規の副作用のあるコマンド実行は不要（Step1・3・7で既に得ている実データを読むだけ。`aim` CLIへの要約依頼のみAPI呼び出しが発生するが、確認は最小回数に留める）
- 手作業での抽出に使った一時的なgrepコマンド・出力は、機能要件の裏付けとして記録に残す以外は破棄してよい

## 検証結果の記録方法（後続ステップから参照する）

- 実装時にこのステップを実行したら、以下を簡潔な箇条書きでこのファイルの末尾（またはこのステップの実行ログ）に追記し、[10-implement-and-verify-extract-script.md](10-implement-and-verify-extract-script.md) 側から要約だけを参照する
  - 対象ログ種別ごとに「実際に欲しかった絞り込み条件」（例: セッションID、hook名、キーワード、直近N件、時刻範囲、ログレベル）
  - 手作業で困った具体的な場面（ファイルサイズ、情報の埋もれ方、巨大行の有無）
  - 対象に含めるログ種別の確定一覧（CLI側／VSCode拡張側のどこまでをカバーするか）
  - `aim` CLIに渡す際に有効だった整形方法の当たり
