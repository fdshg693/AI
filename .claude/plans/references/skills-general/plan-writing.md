# プラン作成時

実装前に書く詳細プランのフォーマット。1機能 = 1サブフォルダ（または小さい機能なら1ファイル）。

## 書く内容（5点のみ）

実装詳細（コードスニペット、具体的なプロパティ定義・メソッド本体など）は書かない。書くのは次の5点だけ。

- **やること**（1〜数行）
- **触るファイル**（新規／変更、パス＋一言）
- **読むべきファイル・実行推奨Grep**（実装前に理解しておくべき既存コード。「何を確認するために読むのか」という観点ごと、優先度ごとにグルーピングする）
- **決定事項・注意点／落とし穴**（判断の理由、既存コードとの衝突、競合状態など事前に言語化できるリスク）
- **ルール更新ポイント**（プロジェクトのルール・規約の格納先に・いつ・何を追記するか。格納先はプロジェクトにより異なる — 既存の慣習に合わせる。新規ルールファイルを作る場合は、対象パスを決めるところまでプランに書く）

コードそのものは実装時に既存の類似ファイルを読んで導出すればよく、プランに書き切る必要はない。

## frontmatter（OKF準拠）

プランファイルの先頭には、Open Knowledge Format (OKF) 準拠のYAML frontmatter（`type`必須、`status`推奨）を付ける。

```yaml
---
type: Plan # 概要ファイル・単一ファイル完結プランはこの値
status: planning-breakdown
---
```

```yaml
---
type: Plan Step # ステップファイル（01-*.md, 02-*.md 等）はこの値
status: implementing-in-progress
---
```

`status`はOKF本来の値（`draft`/`stable`/`deprecated`）ではなく、プランの進捗粒度に合わせた次の6値を使う。

| 値                         | 意味                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| `planning-research`        | プラン中。内容を確定させるための追加調査がまだ必要                      |
| `planning-breakdown`       | プラン中。調査は完了/不要だが、実装できる粒度への分割・詳細化がまだ必要 |
| `ready`                    | プラン確定。調査/実装の実行にはまだ着手していない                       |
| `implementing-started`     | 着手した直後。全体のごく一部にしか手を付けていない                      |
| `implementing-in-progress` | 実行が部分的に完了し、継続中                                            |
| `implementing-done`        | 完了                                                                    |

- 省略時のデフォルトは定義しない。書き始めた時点で`planning-research`か`planning-breakdown`のいずれかを明示する。
- 概要ファイル・単一ファイル完結プランの`status`は機能全体の代表ステータスを手動更新する。個々のステップの詳細な状態は各ステップファイル側のfrontmatterを見る（自動集計はしない）。

## 外部知識が必要な場合: 事前調査ステップ

外部API・外部ライブラリなど、実装前にWeb上のドキュメントを確認しないと決定事項が固まらない機能では、調査を**独立した1ステップ**として先に切り出す。

- 関連しそうなキーワード・URLをまず洗い出し、取得・理解する。
- 調査結果は「要約 + 参照URL」として出力する。読んだページの全文は書かない。後続の実装ステップはこの出力を前提に書き、調査時の文脈を持ち込まない。
- 調査は無駄なページ取得も含めてコンテキストを多く消費するため、実装ステップと同じファイルに混ぜない。

## ステップ分割の目安

- 触るファイルが3〜4個以内で、既存レイヤーをまたぐ新規追加（新しいEntity/Repository/Serviceの新設など）がなく、独立した調査ステップも不要 → 単一ファイルで完結させる
- 新規ドメイン追加、複数レイヤーにまたがる、または外部API・外部ライブラリの事前調査が必要 → `00-overview.md` + ステップ分割ファイル群（`01-*.md`, `02-*.md`…）

## TODO化

各ステップは実行時にTODO（タスク）として追跡できる形に書く。

- **1セッションで完結する小機能**: ステップの「やること」1行をそのままチェックリストの1項目にする。
- **複数セッションをまたぐ・一時中断が前提の機能**: 現状・次にやることを残す軽量なメモ（`CURRENT.md`相当）を別途持たせ、プラン側の✅マークと二重管理にならないよう棲み分ける。

TODOの粒度は「1項目 = 1コミット/1レビュー単位」を基準にする。

詳しい実行時の進め方（進捗記録・後片付け）は [plan-execution.md](plan-execution.md) を参照。

## プランレビュー（サブエージェントに1回依頼する。必須）

プランは分量が多く、誤りが実装フェーズまで気づかれないと手戻りが大きい。詳細プランを書き終えたら（概要＋ステップ分割・単一ファイル完結いずれも）、実装に着手する前に**必ず1回**、サブエージェント機能（利用可能なら）にレビューを依頼する。

- レビュー→修正のサイクルは**1周のみ**。指摘を踏まえて修正したら、その修正に対する再レビューは不要（レビューをループさせない）。
- 依頼文テンプレート:

```
以下のプランをレビューしてください。実装はまだ着手していません。プラン自体の書き直しは不要で、指摘のみ返してください。

# 元の依頼
{ユーザーからの依頼の全文をここに貼る}

# プラン全文
{00-overview.md〜各ステップファイル、または単一ファイル完結プランの全文をここに貼る}

# 確認してほしい観点
- 「やること」と元の依頼の間にズレ・抜け漏れがないか
- 「触るファイル」に不足・誤りがないか（実在するパスか、他に触るべきファイルが漏れていないか）
- ステップ間の依存関係・実行順序に矛盾がないか
- 「決定事項・注意点」に書かれていない隠れたリスク（競合状態、既存コードとの衝突、破壊的変更など）がないか
- ルール更新ポイントの記載漏れ（新規/変更が必要なルールファイルとその格納先）

指摘は「致命的（実装前に必ず直すべき）」「軽微（直さなくても進められる）」に分けて簡潔に列挙してください。
```
